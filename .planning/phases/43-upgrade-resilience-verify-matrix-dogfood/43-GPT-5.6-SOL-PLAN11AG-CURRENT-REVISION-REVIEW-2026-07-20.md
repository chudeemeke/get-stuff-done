## Blocking Findings

### 1. Exact failure ratios can be misclassified as non-failing

`scripts/lib/paired-perf.js` sums safe integer nanosecond samples with `Number`
and classifies the resulting floating-point ratio. The schema permits each
duration up to `Number.MAX_SAFE_INTEGER`, while the aggregate sum can exceed the
safe integer range.

A read-only probe produced schema-valid evidence with reference total
`70000000000000000` and candidate total `87500000000000001`. The exact ratio is
greater than `1.25`, but current recomputation yielded `1.25`, `warn`, and a
successful blocking exit.

**Required correction:** use exact integer sums and rational threshold
comparisons with `BigInt`. Keep floating summaries diagnostic-only. Add
aggregate near-boundary tests using safe individual durations.

### 2. Runner-image provenance is asserted rather than observed

`scripts/bench.js` accepts `--runner-image`, copies it into execution identity,
and rejects only three exact lowercase placeholders. Repeated drift checks
reproduce the caller value instead of observing runtime state.

An arbitrary or stale value can therefore become apparently observed,
digest-bound provenance.

**Required correction:** make the execution-identity adapter return an observed
runner image or OS identity. If a caller supplies an expectation, record it
separately and compare it with the observed value. Plan 11AH may wire the hosted
source, but the observed-versus-expected contract belongs in 11AG.

### 3. Historical comparison can still block

`scripts/check-perf.js` labels baseline mode as diagnostic-only but still exits
with status `1` when the historical comparison fails. That contradicts the
invariant that paired evidence is the only blocking performance authority.

**Required correction:** only paired adjudication may return a performance-
failure exit. Historical comparison must return success while retaining
explicitly diagnostic output. Accepted-regression or calendar state must not
affect process status.

## High Finding

### 1. Warmup alternation can wrap incorrectly

The capture path creates a schedule sized to `measuredPairs` and wraps warmups
through it. The semantic validator repeats the same rule. With
`measuredPairs=11` and `warmupRuns=12`, warmups 10 and 11 have the same order,
yet validation succeeds.

**Required correction:** derive the warmup sequence independently for
`warmupRuns`, preserving parity indefinitely. Add an odd-pair-count and long-
warmup test.

## Medium Findings

### 1. Production Hyperfine and drift plumbing lacks adapter-level tests

Static inspection shows one target command per measured sample: setup precedes
measurement, Hyperfine receives `--warmup 0 --runs 1`, one command is supplied,
and parsing requires one result, time, and zero exit code. Existing tests,
however, replace sandbox creation, preparation, measurement, and cleanup, or
test parsing alone.

**Required correction:** add injected-spawn tests for both metrics and targeted
failures for identity, control, subject, dirty-state, preparation, and post-run
drift.

### 2. The accepted dispersion diagnostic is absent

The accepted design spike requires dispersion alongside pair ratios, median,
order-stratified means, and absolute-noise diagnostics. The implementation and
closed schema contain no dispersion statistic.

**Required correction:** add one deterministic diagnostic-only dispersion
statistic, schema it, recompute it from raw samples, and reject stored
disagreement.
