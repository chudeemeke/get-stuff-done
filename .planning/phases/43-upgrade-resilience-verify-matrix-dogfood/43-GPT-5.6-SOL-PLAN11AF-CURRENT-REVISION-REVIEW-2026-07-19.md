# Verdict: `REVISE`

Plan 11AF is close, and the authentication/cleanup architecture is substantially improved. However, several acceptance properties remain fail-open. These are worker-level defects owned by 11AF—not Plan 11AH’s hosted lifecycle or Plan 11AK’s full lockfile advancement.

I reviewed only the supplied bundle and did not independently execute the reported tests or validate the recorded hashes.

## Plan 11AF blockers

### 1. High — Target composition can fall back to the current source dependency

**Evidence**

Compose receives:

```js
NODE_PATH: path.join(context.projectRoot, 'node_modules')
```

That directory contains the source checkout’s current `@opengsd/gsd-core` version. There is no pre-compose assertion that:

- `workspace/node_modules/@opengsd/gsd-core` exists;
- its real path is contained in the bump workspace;
- its package version equals `options.toVersion`;
- resolution cannot fall through to the source checkout.

**Why it matters**

If target materialization is missing, incomplete, or resolved differently than expected, composition can obtain the current upstream package through `NODE_PATH`. Because the bumped manifest and authority document already say the target version, the resulting output can be labelled as the target without proving that target source actually participated.

That leaves Required Truth 3 and the exact-upstream portion of Truth 8 unproven.

**Minimum corrective action**

- Verify the target package before compose by resolving its `package.json` from the workspace.
- Require its canonical path to be inside the workspace’s `node_modules`.
- Require its version to equal `options.toVersion`.
- Remove the full source `node_modules` fallback. Materialize Ajv in the workspace or expose only an allowlisted composition-tool directory that cannot contain `@opengsd/gsd-core`.
- Add a negative test where the target package is absent but the current source dependency is available; compose must not run.

The minimal target manifest is otherwise a valid 11AF design and does not usurp Plan 11AK.

### 2. High — The smoke digest is syntactically validated, not proven

**Evidence**

`parseSmokeProvenance()` accepts any 64-character hexadecimal value:

```js
if (!/^[a-f0-9]{64}$/i.test(payload.overlayManifestSha256 || '')) return null;
```

The unit test explicitly treats `'A'.repeat(64)` as valid. No expected digest is computed from the composed workspace, packed tarball, or installed package.

**Why it matters**

The gate proves that the installed command printed something shaped like a SHA-256 digest. It does not prove that the digest corresponds to the overlay manifest that was composed, packed, published, and installed.

The receipt’s digest is therefore a fingerprint assertion, not a provenance comparison. Required Truth 8 is not satisfied.

**Minimum corrective action**

- Compute the expected overlay-manifest digest from canonical bytes before publication, preferably also verifying the same bytes inside the bumped tarball.
- Compare the installed smoke result to that exact expected digest.
- Add a test showing that a different but valid 64-character digest produces `smoke_provenance_mismatch`.
- Record expected and observed digest values in the sanitized report.

### 3. High — The npm prepare workaround contaminates executable resolution

**Evidence**

For pack operations, the verifier prepends the source checkout’s binaries:

```js
PATH: [
  path.join(context.projectRoot, 'node_modules', '.bin'),
  context.env.PATH,
]
```

`defaultRunner()` then calls `resolveToolInvocation()` using that modified environment. Consequently, the verifier resolves the outer `npm` executable after adding the source-controlled `.bin` directory.

**Why it matters**

A checkout or dependency providing `node_modules/.bin/npm` can take precedence over the intended npm executable. `shell: false` prevents shell interpolation of the verifier’s arguments, but it does not prevent executable substitution through `PATH`.

Additionally, npm’s unavoidable `prepare` execution invokes its lifecycle command through npm’s own shell machinery. The broad “no command shell” claim is therefore only accurate for the verifier’s direct spawn boundary.

This leaves Required Truth 9 unproven and creates proof-integrity risk.

**Minimum corrective action**

- Resolve trusted absolute npm and Bun executables once against the baseline allowlisted environment.
- Do not use each step’s augmented `PATH` for outer executable resolution.
- Give the already-resolved npm process only the narrow path necessary for prepare.
- Prefer an owned, single-purpose `husky` compatibility shim or a similarly constrained mechanism over exposing every source `.bin` executable.
- Verify the expected static `prepare` command before relying on that workaround.
- Add a test where the project `.bin` contains a fake `npm`; it must never be selected.

### 4. Medium — The temp-root exclusion is lexical, not canonical

**Evidence**

`assertTempParentOutsideProject()` compares `path.resolve()` strings. It does not canonicalize either path using `realpath`.

**Why it matters**

A symlink, Windows junction, alternate canonical alias, or 8.3 path can point an apparently external temp parent back inside the checkout. That can place the run root physically in the source tree and may cause recursive workspace copying or source-tree side effects.

This contradicts the claimed “reject project temp roots nested inside the checkout” boundary and prevents filesystem containment from being fully fail-closed.

**Minimum corrective action**

- Canonicalize the source checkout, temp parent, and newly created run root.
- Compare using platform-appropriate case semantics.
- Reject the run before populating it if its canonical location is inside the checkout.
- Add junction/symlink alias coverage, including a Windows-specific case.

### 5. Medium — Bumped artifact exclusion can be bypassed by npm output

**Evidence**

`excludedPaths` is applied only when `resolveTarballPath()` falls back to scanning the directory. JSON or plain-text npm output returns immediately without checking whether the selected path was already present.

Therefore `pack-bumped` can identify the current tarball as its output and still pass regular-file, containment, size, and digest validation.

**Why it matters**

The structured report can claim that the bumped artifact is the pre-existing current artifact. A normal empty disposable registry will probably expose this during later publication or reinstall, but artifact evidence itself is already inaccurate, and a nonempty registry could mask the error.

Required Truth 10 is only partially proven.

**Minimum corrective action**

- Apply prior-artifact exclusion after resolving a candidate, regardless of whether it came from JSON, text, or directory discovery.
- Compare canonical paths.
- Validate npm pack metadata, or inspect the tarball package manifest, for the expected package name and exact bumped version.
- Add a regression test where pack JSON names the current tarball.

## Registry lifecycle boundary

The worker/external-lifecycle split is coherent and honestly represented:

```json
{
  "ownership": "external-disposable",
  "disposalRequired": true,
  "verifierOwnsRegistry": false
}
```

The receipt supports the local claim that the harness owned and removed the listener, process, and storage. That is sufficient local evidence for this boundary; starting and stopping Verdaccio should not be transferred into 11AF.

The current receipt cannot cure the worker-level proof defects above. After revision, the lifecycle must be rerun and the receipt refreshed. Adding the tested source commit and verifier/report identity to that receipt would make its relationship to the reviewed revision materially stronger.

## Later-plan work — not 11AF blockers

Plan 11AH owns:

- Reproducible hosted Verdaccio startup and configuration.
- Loopback listener and isolated storage ownership.
- Teardown after success, failure, timeout, cancellation, and malformed identity responses.
- Hosted Linux/container evidence and final PR-check integration.
- Refusing to treat worker success as lifecycle completion until disposal is confirmed.

Plan 11AK owns:

- Full root dependency and lockfile advancement.
- Repository-wide target-upstream dogfood.
- Final root composition, distribution, SBOM, and lockfile evidence.

## Minimum closure revision

Plan 11AF can be reconsidered after:

1. Target-upstream resolution is workspace-contained and exact.
2. The smoke manifest digest is compared to an independently computed expected digest.
3. npm is resolved independently of the prepare-compatibility PATH.
4. Temp-root checks use canonical paths.
5. Bumped-artifact identity and newness are enforced across every output path.
6. The focused tests, coverage, full suite, distribution build, linting, and real Verdaccio lifecycle are rerun against the final revision and the receipt is refreshed.
