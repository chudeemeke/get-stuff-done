| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Designing project-local infra without probing canonical tooling | Caught this session: I designed a 5-gate secret-scanning stack before checking aidev's release/quality-gate pipeline. User's "is aidev release already doing this?" surfaced the violation of `feedback_check_framework_first.md` (which I'd been applying to GSD agents only, not to canonical release tooling). | blocking | Before designing pre-commit / release-time / publish-time infra, run: `aidev <subcommand> --help` AND read `~/Projects/ai-dev-environment/scripts/release-manager.sh` for what aidev already does. | Assuming advertised gates are implemented gates | aidev's `quality-gate.sh` documents 8 gates including a Secrets gate. The global SSOT it delegates to does not exist on disk. Running the script printed "ALL QUALITY GATES PASSED" with the headline checks silently skipped — vapourware that misleads every consumer. | blocking | Verify implementation before relying. See `design_advertised_vs_implemented_gap.md` memory: ls the file the consumer references; plant a known failure to confirm the gate catches it; verify exit codes reflect reality. Never trust silent-skip + green-pass. |
| `gitleaks-action@v2` for secret scanning in CI | Requires `GITLEAKS_LICENSE` env var for organization-owned repos. Silently fails on org repos without it. | advisory | Use direct gitleaks binary install instead (curl + tar + install). Pin to a specific release version. Pattern in `ci.yml` `secret-scan` job. |
| Regex-fingerprint allowlist in `.gitleaks.toml` | Embeds the fixture string in HEAD (the very thing the allowlist is excluding). Needless leak risk. | advisory | Use path-based allowlist with documented rationale. The path itself is the canonical home for the test fixture; allowlisting the path keeps the fixture excluded without echoing it elsewhere. |
